## 0. Headline for Will

**The pipeline changed shape twice since the last audit, and generalizing it is now
bigger than "extend a batch list."** `SV_AREAS_AUDIT.md` (2026-07-05) called Wave-0
navmesh generation for the 16 remaining levels "mechanical... the simplest possible
generation case... no GUID remap, no GRID_SHIFT." That was true of the pipeline AS IT
EXISTED on 2026-07-05. Between then and now (`d428266`, `bd61f37`, `09eab66`, tagged
`build13` -> `build17`), the blood-cave recipe grew three more load-bearing mechanisms
that the audit never saw:

1. **Cross-tag rasterization** - the actual cross-level stitch mechanism (disasm-proven
   2026-07-06): area id = 1-based index into the mesh's own GUID list, naming which
   abutting level owns each cell. Single-GUID/own-tagged donors (what the audit's "simplest
   case" would have produced) are now KNOWN to wall - that was attempt #11/#12's failure
   mode, not a hypothetical.
2. **Rigid per-level Y-alignment** - adjacent SV toks are split from one continuous floor
   at a constant +/-2.56u Y offset per pair; that step alone exceeds the engine's tolerance
   and freezes the walk. Needs a BFS-propagated integer correction per connected component.
3. **Deterministic entrance anchoring** - the Y-align BFS root must be the level that
   interfaces FIXED, non-regenerated data (the entrance), or the fix silently breaks the
   one thing that can't be re-verified internally. This shipped as a hard assert
   (`09eab66`) after an arbitrary root shifted Random09A -3u and walled the cave mouth
   while every interior gate passed.

**Every one of these is BLOOD-CAVE-SPECIFIC CODE today** (`BC_TOKEN='xbloodcave'`,
`R09_KEY` hardcoded, `OWN_GUID_OVERRIDE` hardcoded to Random09A, three new gate scripts
in `tools/debug/` that hardcode `HV_KEY`/`R09_KEY`/a literal `CHAIN` list of blood-cave
basenames). None of it is a generic library yet. Generalizing means re-deriving each
mechanism per area, not calling a function with different arguments.

**Second headline: the blood-cave walk test itself is still unconfirmed.** `build17` was
deployed 2026-07-06 18:12; CLAUDE.md and the ledger both say the in-game walk test is
PENDING. The "proven pipeline" the task brief refers to is proven by static gates
(G1-G4, frontier check) and Frida runtime probes, not yet by Will walking through the
door. Recommend treating the very first area campaign wave as a validation of the
generalization approach itself, not just new content - see Section 6.

**Third headline (unchanged from the prior audit, reverified below): the navmesh axis is
the easy 80% of the work and the entrance axis is the hard 20%.** Five of six areas lost
their entrance because a shared SVAERA level replaced the SV version that carried the
portal/warp record. That architectural choice (blob-patch the shared AE level vs. a
fragile quest teleport) is still the central decision, and is now sharpened by the Y-align
lesson: blob-patching a shared level means that level's toks were never generated by our
pipeline at all, so there is no "constant Y offset" to measure against it - the entrance
anchor discipline (Section 4) must treat every shared-level junction as a hard-fixed
reference, exactly like Random09A/HiddenValley01.

## 4. What generalizing the pipeline requires, per mechanism

`gen_bc_navmeshes.py` today hardcodes: `BC_TOKEN = 'xbloodcave'` (the cluster filter),
`R09_KEY` + `OWN_GUID_OVERRIDE` (the one blob-swapped entrance level), and the Y-align
anchor's `_root_rank` (Random09A > OWN_GUID_OVERRIDE > alphabetical). The three debug gates
(`entrance_landing_check.py`, `engine_corridor_full.py`, `seam_delta_check.py`) hardcode
`HV_KEY`/`R09_KEY` and a literal `CHAIN` list respectively. None of this is parameterized
yet. Per area, generalizing needs:

1. **Cluster token / level list.** Trivial for the 5 single-level areas (a literal
   one-element list). Secret Place needs the 11-level list (already enumerated in Section 1
   and the prior audit's neighbor-GUID map, which is still structurally valid - it predates
   only the Y-align/cross-tag MECHANISM, not the adjacency FACTS).
2. **GRID_SHIFT entry.** **NONE NEEDED for any of the 16** - reverified 2026-07-06, all 16
   sit at their SV-original grid positions and are already disjoint from everything. This is
   the one respect in which these areas are simpler than the blood cave (which needed a
   3001.8u relocation to clear a GUID-gate collision). Do not add a GRID_SHIFT entry unless
   a specific area is later found to need one.
3. **Entrance-anchor level = the level interfacing native/fixed geometry.** This is the
   deepest generalization gap. For the blood cave it is Random09A, because that level's
   blob is SWAPPED IN at an AE GUID slot the surface (HiddenValley01) already binds to. For
   the 5 isolated-island areas, THERE IS NO SUCH LEVEL YET, because the entrance mechanism
   is "restore a lost record in a shared AE level," not "swap a blob at a kept AE slot."
   Two sub-cases:
   - **Uber Dungeon / Boss Arena / Garden of Merchants (blob-patch route, Section 5 option
     A):** the anchor is the PATCHED SHARED LEVEL itself (`maze03`, `startingfarmland06d`/
     `hiddenvalleyborder04`). Since that level's own `0x0b` is NOT regenerated by our
     pipeline (it stays AE's untouched navmesh), the isolated area's donor becomes the
     "Random09A" of this junction: its Y-align component root, its `OWN_GUID_OVERRIDE`
     equivalent (its own GUID needs no override since it is a genuinely new/kept SV-only
     GUID, not fighting for an AE slot) - BUT its generation must still measure/zero any
     constant Y offset against the FIXED point the shared level's re-injected `0x14`/`0x06`
     descriptor will land the player at. That fixed point does not exist yet until the
     blob-patch is authored, so navmesh generation and the entrance-record restoration are
     NOT independent work items for these three areas - order matters (Section 6).
   - **Secret Place (Section 4's internal chain):** the chain has its own internal
     entrance-anchor question independent of the entry restoration - once inside via
     `behindthesp`, the forest-chain and rogue-camp-trio seams need their own Y-align BFS
     root, most naturally `behindthesp` (or `darkforestenter`, the first `urder.qst`
     teleport target) since those are what the quest's fixed teleport coordinates target.
4. **Seam-graph particulars.** Only Secret Place has one (Section 2.1). The other 5 areas
   are single levels - **seam work is moot for Uber Dungeon, Boss Arena, Garden of
   Merchants, Sparta Crypt L2, and Cold Tombs.** Their navmesh generation is "one level,
   own GUID, no neighbors" - the cross-tag mechanism only matters at the junction with the
   (unregenerated) shared level, not internally.
5. **Per-area G2-equivalent gate.** `AREA_WIRING_RECIPE.md`'s own stated lesson: "the oracle
   must test the AREA'S INTERFACE TO THE OUTSIDE, not start inside it." Each area's entrance
   junction needs its own landing-check script (parameterized `HV_KEY`/`R09_KEY` equivalents
   become e.g. `MAZE03_KEY`/`CRYPT_FLOOR1_KEY` for uber dungeon). This is currently
   copy-paste-and-retarget work, not a generic tool - budget for it explicitly per area
   rather than assuming Wave-0-style "just add to a list."
6. **G3/G4 equivalents.** Only meaningfully needed for Secret Place (a real multi-level
   chain). For single-level areas, G3/G4 degenerate to "does the one level's own-GUID mesh
   cover its own floor" - a much weaker check than the blood cave's chain reachability, but
   still worth a one-line sanity script per area rather than skipping verification entirely.

**Where the blood-cave recipe does NOT transfer cleanly (flagged explicitly, per the
task's ask):**
- The **entrance mechanism itself** does not transfer. Blood cave = blob-SWAP at a kept AE
  GUID slot (no shared-level edit beyond the swap). Four of five remaining areas need a
  **blob-PATCH of a shared level's `0x05`/`0x14`/`0x06`** (append new data to an existing
  AE-authored level, not replace it wholesale) - a related but distinct and less-rehearsed
  operation. `INJECT_SPECS`/`inject_into_0x05_v11` exists and is documented as the LIVE,
  safe path (`AREA_WIRING_RECIPE.md` Phase D.2); the `0x14`/`0x06` GridEntrance-binding
  APPEND (as opposed to the default 20-byte non-binding payload) is flagged in the playbook
  itself (Section 4, Strategy B) as "the only piece not yet built."
- The **Y-align anchor concept** assumes a fixed external reference the pipeline does not
  regenerate. For the blob-swap case (blood cave) that reference is a NATIVE portal landing
  authored entirely outside our tooling. For the blob-PATCH case (the other 4), the
  "fixed" reference is a record WE are about to inject into someone else's level - it only
  becomes fixed after Phase D authors it, creating a real ordering dependency Section 6
  makes explicit that the blood cave didn't have (Random09A's entrance was fixed before any
  navmesh work started).
- **Garden of Merchants' two-shared-level entrance** has no blood-cave precedent at all
  (blood cave touches exactly one shared level, Random09A's own slot). Patching two
  independent AE levels to cooperate (or picking just one, per the recipe's own
  recommendation) is new ground.
- **Sparta Crypt L2** may have no intended entrance to restore, which the blood-cave
  recipe has no analogue for either (every fixed area there had inarguable original SV
  connectivity).

## 5. Entrance-restoration mechanism decision (carried forward, sharpened)

Still the central Will-decision, reverified unchanged in the current map:

- **(A) Engine-native blob-patch of the shared AE level** (append the lost SV portal/warp
  record + its `0x14`/`0x06` binding into the KEPT AE blob). Matches the spirit of the
  Random09A fix (an existing-slot edit, not a wholesale swap, so it is arguably LOWER risk
  than the blood cave's own fix in one respect: no GUID-slot juggling). Touches: `maze03`
  (fixes 2 areas), `startingfarmland06d` and/or `hiddenvalleyborder04`, `scrabledeggs_floor06`.
  Reversible, Steam-clean (map-data only). **Newly sharpened risk (2026-07-06): whatever
  fixed landing point this patch creates becomes a Y-align anchor requirement for that
  area's own navmesh generation - the two are coupled, unlike Section 4's other assumptions
  suggested when read in isolation.**
- **(B) Quest teleports.** Cheaper, no shared-level edit, but the playbook flags this
  FRAGILE class as having broken twice already in this exact project (state bakes into
  saves; the `REPEAT_STEPS=200` `OnLevelLoad` idiom). Not recommended for persistent-area
  entry - reserved for genuine scripted events only, per the playbook's own rule.

**Recommendation unchanged: (A) for all four shared-level-loss areas.** Sparta Crypt L2 is
the one area where neither may be warranted (Section 2.5) - recommend a scoping decision
(ship vs. drop) before spending any implementation effort there.

## 6. Sequenced campaign plan (ordered by player-visible value and risk)

Ordering rationale: prove the generalized recipe once, cheaply and low-risk, before
committing to the more valuable but structurally novel work (two-level or multi-junction
patches). This also deliberately interleaves with the still-pending blood-cave walk test
rather than assuming it will pass unchanged.

### Wave 0 - WAIT for the blood-cave walk test (gating precondition, not a work item)

Do not start generalization work that assumes the Y-align/cross-tag/anchor recipe is
correct until Will's in-game walk confirms `build17`. If the walk test fails, the fix will
likely change one of the three mechanisms in Section 0 again, and any area-specific work
done in parallel risks being built on the wrong foundation (this project's own history:
11 prior "fixed" builds each looked correct by their contemporary gates and walled anyway).
Low cost to wait; the areas below are not blocked on anything else.

### Wave 1 - Single-level navmesh generation dry-runs, NO entrance work (LOW risk, do first)

Extend `gen_bc_navmeshes.py`'s batch (or a parallel small driver, to avoid further
overloading an already-large blood-cave-named file) to generate `0x0b` donors for the 4
single-level, no-internal-seam areas with a real chance of shipping (crypt_floor1,
boss_arena, gardenofmerchants, spartacryptlevel2 - defer coldtombs per Section 2.6). Each
is "own GUID only, no neighbors, no GRID_SHIFT" - genuinely the simplest generation case,
UNCHANGED by the Y-align work (a single isolated level has no seam partner to be offset
against, so the Y-align BFS component is trivially just itself at shift 0). This produces
walkable interiors with **no entrance yet** - useful for validating generation in isolation
and for the eventual G2-equivalent gate's "does the mesh cover the level" half, without
yet committing to any blob-patch design. Verify via `--dry-run` self-checks only; do not
inject into the merged map until the entrance side is designed (an unreachable-but-walkable
level is a fine intermediate state, an injected-but-untested one risks a wasted deploy
cycle).

### Wave 2 - Uber Dungeon + Boss Arena via the shared maze03 patch (MEDIUM risk, HIGH leverage)

Fixes two areas with one shared-level patch (`maze03`). Recommended as the FIRST
entrance-restoration work because:
- it is the smallest blast radius (one shared level, not two);
- both destination quests (`bossarena.qst`'s DynGridEntrance-open, uber dungeon's existing
  return NPC) are already ported/placed and just need the entrance record to exist;
- it validates the blob-patch + Y-align-anchor coupling (Section 4/5) cheaply before
  attempting Garden of Merchants' two-level version.

Steps: (1) extract SV maze03's `portal_olympianarena1.dbr` placement + its `0x14` binding
payload (UniqueIds + destination GUID at offset 32) from the pristine upstream blob; (2)
append into AE maze03's `0x05`/`0x14` via the `INJECT_SPECS`/`inject_into_0x05_v11` LIVE
path (per `AREA_WIRING_RECIPE.md` Phase D.2 - NOT the deprecated `generate_default_0x14`
path, which corrupted a blob previously); (3) generate crypt_floor1's and boss_arena's
`0x0b` donors anchored against the new fixed landing point the maze03 patch creates,
mirroring the Random09A anchor discipline; (4) build a maze03-specific G2-equivalent gate
before deploying; (5) confirm boss_arena's own downstream binding (may need a second
`0x14` payload depending on how SV originally chained maze03 -> crypt_floor1 ->
boss_arena - inspect during implementation, flagged as an open unknown in the prior audit
and still unresolved here).

### Wave 3 - Secret Place entrance + internal chain (HIGH value, HIGHEST effort)

The richest area (11 levels, 2 questlines already ported and content-complete) but the
only one needing the FULL blood-cave-style seam machinery internally (cross-tag +
Y-align across the forest chain and rogue-camp trio) in addition to a shared-level
entrance patch (`scrabledeggs_floor06`). Sequence internally: (1) generate the internal
chain's navmeshes with cross-tagging + Y-align, anchored at `behindthesp` (or
`darkforestenter`, whichever the `urder.qst` teleport coordinates most directly target -
decide during implementation by checking which the quest touches first); (2) verify the
internal chain with a Secret-Place-specific G3/G4 equivalent; (3) separately, patch
`scrabledeggs_floor06` to restore the entrance portal into `behindthesp`; (4) gate the
entrance junction with its own G2 equivalent; (5) confirm `widowletter.qst` fires once
reachable (static verification only - no map rebuild expected). This is the highest
player-visible value (a full questline zone) and the highest effort - schedule it after
Wave 2 proves the blob-patch + anchor pattern works on the simpler single-level cases.

### Wave 4 - Garden of Merchants (MEDIUM-HIGH effort, novel two-level patch)

Richest content by record count (172) but no ported questline currently found - it is a
walk-in shopping hub, not a story quest. Novel because it is the only area needing
POSSIBLY TWO shared-level patches (`startingfarmland06d` and/or `hiddenvalleyborder04`).
Recommend the prior audit's own steer: patch ONLY `startingfarmland06d` first (minimize
shared-level footprint) and confirm in-game before considering the second entry point:
players lose nothing structurally if only one of the two original entrances is restored.

### Wave 5 - Sparta Crypt L2 (LOW value; scope decision before any implementation)

Reverified: genuinely no binder exists anywhere, even in pristine SV. Recommend Will
explicitly decide ship-vs-drop before any generation or patch work; if shipping, it is a
single-level case like Wave 2's components (no seam work), but the "intended entrance" is
a research question (inspect `spartaoptcata01` for a stair/geometry SV cut) rather than a
known byte-level target the way the other four are.

### Wave 6 - Cold Tombs

No work. Keep the 148-byte stub, matching the 7 blood-cave ocean-scenery levels. Document
as intentionally stubbed; do not revisit unless new upstream evidence of an entrance
surfaces (none found in this pass).

## 7. Per-area gate checklist (mirrors the blood cave's Phase C, generalized)

For EVERY area before any deploy:

- [ ] **Donor generation self-checks pass** (round-trip identity, 3 tilesets, GUIDs
      resolve, no `GRID_SHIFT` regression if one is ever added).
- [ ] **Anchor gate**: the area's Y-align BFS root is the level interfacing fixed/external
      data (the entrance junction), with a hard assert on shift==0 there - not the
      arbitrary first entry. For single-level areas this is trivially satisfied (no BFS
      needed) but still assert it explicitly rather than assuming.
- [ ] **Cross-tag sanity**: for multi-level areas (Secret Place only), every donor listing
      neighbors has at least one neighbor-tagged cell (the build13 failure mode check

## 8. Top risks (summary; detail inline above)

1. **Foundational risk**: the blood-cave walk test (build17) has not yet been confirmed by
   Will. Eleven prior builds each looked correct by their contemporary static gates and
   walled in-game. Generalizing before this confirmation risks propagating a wrong
   mechanism six more times.
2. **Blob-patch is a less-rehearsed operation than blob-swap.** The blood cave's fix was a
   full-level SWAP at a kept GUID slot; four of five remaining areas need a surgical APPEND
   into a shared level's `0x05`/`0x14`/`0x06` sections. The GridEntrance-binding append path
   is explicitly flagged in the playbook as "the only piece not yet built."
3. **The Y-align anchor and the entrance-record restoration are ORDER-COUPLED** for the
   blob-patch areas, unlike the blood cave where the anchor (Random09A's native mouth) was
   fixed before any navmesh work began. Generating a donor before the shared-level patch
   exists means anchoring against a landing point that doesn't exist yet.
4. **Garden of Merchants' two-shared-level entrance has no precedent in this project.**
   Recommend the single-level-first mitigation already in Wave 4.
5. **Verification tooling is 100% blood-cave-hardcoded** (three debug gate scripts + the
   generator itself). Each area needs its own retargeted gate scripts, not a config flag -
   budget real effort here, not "mechanical extension."
6. **Sparta Crypt L2 may have no valid entrance to restore at all** - a scope question, not
   an implementation risk, but worth resolving explicitly rather than defaulting to "port
   it like the others."
7. **Concurrent build-file edits** (uncommitted working-tree changes at the time of this
   scoping pass touched `tools/build_section_surgery.py`, `tools/hybrid_merge.py`,
   `tools/fix_mc_output.py`, and untracked `tools/populate_svbake_records.py`,
   `tools/reconcile_seam_heights.py`, `tools/setup_svbake_world.py`, `tools/wrl_format.py`)
   mean the exact line numbers and function shapes cited in the playbook/ledger may drift
   before any of the above waves start implementation - re-grep the cited symbols rather
   than trusting line numbers when work begins.
